# 刷新性能优化与验证

2026-10-22，在 Windows 本机对 easygit 自身仓库测量。相同分支与提交，展示 10 条历史，本地与上游同步。使用 debug 测试构建，每组连续刷新 5 次；测量不访问网络、不写入仓库。基线工作区有 2 个变化文件，优化后有 7 个，新增文件来自本次代码修改。

| 项目 | 优化前 | 优化后 |
| --- | --- | --- |
| 每次仓库快照的 Git 调用 | 32 | 首次 10，之后 9 |
| 5 次平均刷新耗时 | 2786.1 ms | 676.5 ms |
| 提交归属判断 | 每条提交额外执行祖先查询 | 使用现有拓扑日志传播两侧可达关系 |
| 持续无变化时自动刷新 | 每 8 秒一次 | 完成读取后等待 8 → 16 → 30 秒 |
| 窗口失焦或隐藏 | 可见但失焦仍轮询；隐藏时定时器仍唤醒 | 取消轮询定时器，回到窗口立即读取 |
| 相同快照的差异、脚本读取 | 每次重读 | 跳过，保留快照对象 |

基线耗时：2788.8、2912.1、2794.4、2814.9、2620.5 ms。

优化后耗时：739.0、672.5、694.3、647.0、629.8 ms。

以上约 76% 的耗时下降仅适用于本次仓库快照测量，不代表整机 CPU 百分比下降。未测量发布版 WebView、应用和 Git 子进程的合计 CPU 占用；耗时受仓库大小、磁盘和系统负载影响。

## 实现

- `git/history.rs` 利用 `git log --topo-order` 保证子提交先于父提交的顺序，从 HEAD 和上游向父提交传播可达标记。保持原有 10 条限制，不缓存提交图，不增加 Git 调用。
- `git.rs` 在现有 `for-each-ref` 中同时读取 HEAD、分支和上游信息；未产生首个提交、detached HEAD 和自定义 fetch 映射保留回退。成功读取的 Git 版本在进程内复用。
- `git/revision.rs` 为快照生成轻量指纹，包含结构化状态、索引、变化文件的大小/修改时间/类型，以及 package.json 和包管理器锁文件的元数据。已经是 M 状态的文件再次编辑、脚本变化和包管理器变化仍会发布快照。
- 静默刷新仅在指纹一致时跳过状态发布。手动刷新、写操作和 fetch 完成后的刷新仍发布新快照；手动请求加入正在进行的静默读取时也会强制发布。
- 轮询等待前一次读取结束，失败后使用 8 秒间隔重试；关闭仓库、切换项目、隐藏或失焦时清理对应定时器。已有请求可能完成，后台 fetch 与用户操作不受暂停轮询影响。

持续在前台但无操作时，外部修改的检查间隔最长为 30 秒（另加读取时间）；回到窗口立即检查。指纹使用元数据避免每次读取全部变化文件的内容；若外部工具同时保留文件大小和修改时间，使用手动刷新可强制重读。

## 验证与复测

前端 113 项测试、Rust 72 项测试通过，另有 1 项手动性能测试默认忽略；TypeScript 检查、Vite 生产构建、Cargo Clippy 和格式检查通过。

真实浏览器配合模拟 IPC 验证：连续 5 次相同版本的读取，差异和脚本读取次数均不增加；版本变化和手动刷新仍各重读一次。真实 Git 测试覆盖分叉、合并、超过 10 条的历史、异常提交时间、无提交分支、detached HEAD、worktree，以及本地、自定义、缺失上游。提交可达结果与 `git merge-base --is-ancestor` 对照一致。
